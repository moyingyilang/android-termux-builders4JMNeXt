# 走 GitHub Releases 分发的应用：更新路径怎么设计

适用于"自己打包、自己发 Release、不走应用商店"的项目（Android APK + 桌面 JVM 包都算）。

## 一、先把"更新"拆成三件事，别混为一谈

| 能力 | 含义 | 是否需要用户操作 |
| --- | --- | --- |
| **检查更新** | 拿到远端最新版本号，和本地比 | 不需要 |
| **一键更新** | 应用内给出**正确那个包**的直链/下载 | 点一下 |
| **热更新** | 不装包、重启就换掉逻辑 | 不需要 |

三者难度天差地别。**大多数"更新做不好"的抱怨，根因在第二件而不是第三件**：
检查更新往往早就做好了，坏在"只给一个发布页链接"。

## 二、最常见的坑：发布页附件名里没有架构

实测案例：Android 附件命名 `Android-full-<版本>.apk` / `Android-lite-<版本>.apk`，
**名字里不含架构**（一个 APK 同时含多个 ABI 的 native 库，`aapt2 dump badging` 的 `native-code` 能确认）。
于是 arm64 用户被告知"有新版本"后，到发布页按"arm64 版"去找，**找不到任何带 arm64 字样的文件**，
反馈就是"**总是获取不到更新包**"。

**正确做法**：由**应用自己**算出该下哪个包并给**直链**，同时把"一个包支持哪些架构"写在界面上：

```
附件名 = "Android-" + (lite ? "lite" : "full") + "-" + 归一化版本 + ".apk"
直链   = "https://github.com/<repo>/releases/download/v<版本>/" + 附件名
```

**要点**：
1. 版本号必须**归一化**（去掉 `v` 前缀与 `.lite` 这类变体后缀），否则拼出的文件名根本不存在；
2. 直链里的 tag **必须带 `v` 前缀**；
3. 这些拼接写成**纯函数 + 单元测试**，命名与打包脚本严格对应 —— 将来改命名规则时测试会立刻失败提醒；
4. 桌面端按 `os.name` / `os.arch` 选包，**把"内含多架构运行时"的统一包排第一**。

## 三、热更新：编译期做重活，运行时轻量替换

**关键事实**：Android 8 起"未知来源安装需用户确认"限制的是**安装 APK**；热修复框架运行时加载的是
**补丁 dex/jar**，不受该限制。所以只要编译期把钩子埋好，运行时替换补丁确实可以做到无感。

| 方案 | 编译期（重活） | 运行时 | 风险 |
| --- | --- | --- | --- |
| **Robust** | 插件给每个方法插桩（变更重定向） | 下载补丁 dex → 自定义 ClassLoader → **立即生效** | 维护停更；Android 新版本收紧 ART/非 SDK 接口 |
| **Tinker** | 基线 APK + dex 差分补丁 | 下载 → 合并 → **重启生效** | 停更；不能加 Manifest 组件 |
| 插件化（Shadow 等） | 宿主与插件分离编译 | 下载插件加载 | 架构级重写 |
| 官方 Play（AppUpdateManager/AAB） | 模块化 | Play 下发 | **必须走 Google Play** |
| 桌面 **update4j** | 可替换的 jar 集 + 更新描述 | 下载 → 退出替换 → **重启** | 不是"运行中生效" |
| 桌面 JRebel / DCEVM | 商业授权 / 改版 JDK | 真类结构热替换 | 成本高 |

**边界**（补丁改不了的东西）：权限与 Manifest 组件、native 库（`.so`/`.dll`）、资源大部分改动；只能改已有代码。

## 四、桌面 JVM 的现实上限

- 运行中的 JAR 会被系统锁住（Windows 尤其），**换不了自己**；
- JVM Instrumentation 只能改**已有方法体**，不能加类/方法/字段；
- 所以现实做法是"下载到临时目录 → 退出 → 小脚本替换 → 重启"，或用 **update4j** 这类自更新库。

## 五、写在最后：别把"热更新"当成"更新没做好"的借口

先把**检查更新 + 一键更新**做扎实（纯函数 + 测试 + 界面上写清该下哪个包），
再评估热更新是否值得引入框架与长期兼容性负担。多数项目做到第二件就够了。
